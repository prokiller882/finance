# Ревью: PRD против кода

**Предмет:** `prd.md` (draft, 2026-11-22) и репозиторий `/mnt/c/Users/user/programm/test-app` (HEAD `f102ef5`).
**Источники истины:** `AGENTS.md` (поведение), `ROADMAP.md` (статус), `DESIGN.md` (визуал), код.

## Вердикт

PRD **совместим по духу, но не готов к реализации как есть**. Три контура (баланс, P&L, ДДС)
уже есть и названы в PRD теми же словами; половина FR описывает фактическое поведение точно
(FR-1, FR-4, FR-5, FR-6, FR-7, FR-8, FR-11, FR-12, FR-13, FR-38, FR-46, FR-47, FR-49, FR-50).
Но четыре блока требуют либо нового домена со схемой v4 (обязательства, норма сбережений,
разметка категорий), либо переопределения существующих сущностей (бюджеты), а два требования
прямо противоречат выпущенному поведению (удаление «Ближайших платежей», пять периодов на обзоре).
Плюс FR-18 («в P&L только проценты, в ДДС весь платёж») невыразим текущей моделью операций и
отчётов без решения о новой форме проводки. **Блокеры до кодинга: FR-18/17, FR-45, FR-44, FR-34.**

### C3. FR-18: «в P&L только проценты, в ДДС весь платёж» невыразимо текущими отчётами (блокер)

| | |
|---|---|
| PRD | `prd.md:256-259`: «Проценты = остаток × ставка / 12… В P&L попадают только проценты; в ДДС — весь платёж; в балансе долг уменьшается на тело» |
| P&L | `js/reports/incomeStatement.js:10-38` — суммы по `type === 'expense'`, без иных измерений |
| ДДС | `js/reports/cashFlow.js:5-15` — `totalOut` из тех же `groupTransactionsByCategory('expense')`; переводы исключены из итогов и показаны справкой (`cashFlow.js:17-32`, `reports.js:184-189`) |
| AGENTS.md | «Переводы не входят в P&L и итоги ДДС; показываются справочной строкой» |

Две возможные проводки обе ломают требование:

1. **Одна операция-расход 25 000 ₽** → в P&L и в ДДС попадёт 25 000, а не 7 000/25 000.
2. **Две операции: расход 7 000 (проценты) + перевод 18 000 (тело)** → P&L верен, ДДС покажет
   `Списания 7 000`, что противоречит «в ДДС — весь платёж», а перевод уйдёт в справку.

Второй вариант вдобавок ломает внутренний инвариант `discrepancy`:
`cashFlow.js:33-34` проверяет `(totalIn - totalOut) - (closing - opening) = 0`. Если тело уходит
переводом на «счёт долга», которого нет в `state.accounts`, `closing - opening` уменьшится на 18 000,
а `totalOut` — нет. Сейчас инвариант держится только потому, что переводы двигают два реальных счёта
и взаимно сокращаются. **FR-18 требует новой формы проводки и правки отчётов — это дизайн-решение,
а не поле в форме.**

### 2.2 Обязательная миграция

1. `js/schema.js:3` — `SCHEMA_VERSION = 4`.
2. `migrate()` (`storage.js:46-149`) должен **умолчаниями** добавить: `obligations: []`,
   `account.savingsPercent: 0`, `transaction.sourceTransactionId: null`, `transaction.skipSavings: false`,
   `category.mark: null`. Без этого `validateState()` отвергнет старую копию: единственная проверка
   версии — `state.schemaVersion !== SCHEMA_VERSION` (`storage.js:175-177`), а `migrate()` переписывает
   `schemaVersion` в актуальный (`:78`) — то есть старый файл пройдёт проверку версии и упадёт на
   отсутствующих полях новой сущности.
3. Проверки формы массивов по образцу `storage.js:63-71` (`obligations != null && !Array.isArray → INVALID_STATE`).
4. `validateState()` (`storage.js:167-414`): ссылка `obligation.accountId → accounts`; уникальность
   пар `obligationId:date` (по образцу `:378-383`); `savingsPercent` 0…100 и сумма ≤ 100 по активным
   накоплениям; `sourceTransactionId → transactions` и `sourceTransactionId !== id`;
   `skipSavings` только у `type === 'income'`.
5. `models/index.js` + `js/models/obligation.js` по контракту `create/fromJSON/validate/toJSON`
   (`docs/extending.md:38`).
6. `seed.js`: `obligations: []`, `savingsPercent: 0` у двух seed-счетов.

### 2.3 Ключевая проблема раскладки платежа

Проценты зависят от остатка долга на дату платежа, а остаток — от всех предыдущих оплат.
Два варианта:

* **Хранить snapshot** `principalMinor/interestMinor` в момент оплаты. Детерминированно, но занимает
  место и требует пересчёта цепочки при удалении/правке прошлого платежа (C8), иначе долг «уплывёт».
* **Пересчитывать при чтении** (реплей оплаченных вхождений по дате). Полей не нужно, но любая
  правка прошлого платежа меняет проценты всех последующих — а они уже показаны в P&L за закрытые
  периоды. Отчёты станут «плавающими».

PRD этого не решает. Рекомендация: snapshot + явное правило «правка/удаление оплаты пересчитывает
все последующие вхождения обязательства» (и это надо записать как FR, иначе нечего тестировать).

### 2.4 Импорт старой копии

Цепочка: `parseImportFile()` → `migrate()` → `validateState()` (`storage.js:543-568`) → `store.replace(next, {persist:true})`
(`app.js:283-288`), состояние заменяется целиком.

* **v3 → v4**: работает, если все новые поля имеют умолчания. Иначе `StorageError('INVALID_STATE')`,
  и пользователь видит тост «Данные не прошли проверку: …» (`settings.js:329-332`).
* **v2 → v4**: сейчас проходит одной нормализующей функцией без ветвлений по версии
  (`storage.js:46-149`; `ROADMAP.md:16` обещает «миграция v1/v2 → v3»). Отсутствие `schemaVersion`
  трактуется как 1 (`storage.js:51`). Значит, v2-копия с `budgets`, но без `plannedPayments`
  получит пустые массивы — это и есть «без потерь». Новые умолчания просто добавятся.
* **v4 → v3** (старый кэшированный билд PWA): `fail('UNSUPPORTED_VERSION')` (`storage.js:52-53`).
  Это реальный сценарий, а не теоретический — см. риск R5.
* **v3 → v4 при обычном запуске**: `readState()` мигрирует, `loadState()` сразу
  `saveState(stored)` (`storage.js:453-465`) — состояние перезаписывается при первом открытии.
  Если миграция сломана, данные уйдут в `finance-tracker:corrupt` (`:416-423`), а в приложении
  окажется **seed** — визуально это «всё пропало», с одной строкой в консоли. Для схемы v4 это
  главный риск потери данных.

## 4. Риски реализации под этот стек

### R1. `structuredClone` и plain-объекты

`store.commit()` клонирует состояние через `structuredClone` (`store.js:18`); `AGENTS.md`:
«В `state` и localStorage — только plain-объекты… экземпляры классов туда класть нельзя».
Конкретные ловушки для новых фич:

* Геттер `obligation.remainingPrincipal` с расчётом процентов — после `commit` геттер исчезнет
  (клон plain), и UI начнёт показывать `undefined`.
* `Object.assign(account, normalizeAccountInput(...))` (`app.js:230`) — если `savingsPercent`
  не попадёт в возвращаемый объект `js/accounts.js:40` (`{ name, kind, openingBalance }`),
  он **молча обнулится** при любом редактировании счёта. Это самая вероятная ошибка в FR-2.
* `Date`/`Map` в новом состоянии — `structuredClone` их сохранит, но `JSON.stringify` в
  `saveState` (`storage.js:445`) превратит в строку/`{}`; `validateState` упадёт.

### R2. Квота localStorage

~5 МБ на origin, и этот origin делит хранилище с другими проектами (`AGENTS.md`: ключ
`finance-tracker:v1` на `prokiller882.github.io`). Риски PRD:

* Каждый приход с нормой сбережений создаёт **N переводов** (FR-23) — это N полных объектов
  операции (id, note, createdAt, updatedAt…). При 10 приходах в месяц и 2 счетах — +20 записей.
* Если раскладку платежа хранить как отдельные `obligationPayments` на каждое вхождение за весь
  срок кредита (15 лет × 12 = 180), это +180 объектов — терпимо, но если генерировать
  **ожидаемые** вхождения для обязательств в `state` (вместо вычисления из правила), это уже тысячи.
  Сейчас ожидаемые вхождения не хранятся принципиально (`models/paymentOccurrence.js:14-17`).
  PRD FR-16 не говорит, какой подход; надо зафиксировать «генерировать на чтение».
* Механизм уже есть: `commit()` возвращает `false`, UI показывает «возможно, закончилось место
  в localStorage» (`transactionSheet.js:295-298`). Автопереводы и обязательства должны
  обрабатывать этот отказ так же, а не «молча».

### R3. Целые копейки и проценты

* Деньги — целые копейки, `NaN`/float недопустимы (`AGENTS.md`). Ставку **нельзя** хранить
  как float: `12.5` % → `remaining * 0.125 / 12` даёт плавающую ошибку. Нужны базисные пункты
  (например `annualRateBp = 1250`) и `Math.floor(remaining * bp / 120000)`; PRD («годовая ставка»,
  «округление вниз до копейки», FR-18) этого не описывает.
* `parseAmount()` не подходит для процентов и ставок: он возвращает копейки и запрещает `-`
  (`format.js:9-18`), допускает максимум 2 знака после запятой. Для «10%» нужен отдельный парсер.
* Процент сбережений как целое 0…100 исключает 0,5 %; PRD говорит «процент», не уточняя шаг.
* Остаток от округления: `income * pct / 100` с `floor` по каждому счёту оставляет 1–N копеек
  на счёте-источнике. При сумме процентов = 100 % это максимум несколько копеек, но правило
  «остаток остаётся на счёте прихода» надо записать, иначе тест FR-23 неоднозначен.

### R4. Даты: строки `YYYY-MM-DD`, локальное vs UTC

* Сравнение — строками (`format.js:94-97`); арифметика — только `parseISO()/addDaysISO()`
  (`format.js:46-59`), иначе UTC сдвинет день (`AGENTS.md`).
* FR-28: «дни до поступления» — это `parseISO(to) - parseISO(today)` в локальном времени,
  не `Math.round((d1-d2)/86400000)` от UTC-полуночи на переходе DST.
* «Месяц от сегодня» (допущение §10, `prd.md:659`): нельзя писать `+30 дней`. Нужен локальный
  календарный месяц: `monthRange`/`shiftMonthKey` уже локальны (`format.js:77-92`), но «та же
  дата следующего месяца» упирается в 31-е → используйте `clampDay()` (`recurrence.js:20-22`),
  иначе 31 января + 1 месяц даст 3 марта.
* `seriesStartDate()` уже решает границу «не раньше месяца создания» через локальный `monthKey`
  (`recurrence.js:24-39`) — обязательства (FR-16) должны переиспользовать это, а не писать своё.
* `statusForDate()` (`payments.js:18-22`) — единственное место, где просрочка определяется
  от `todayISO()`; лимит (FR-27) должен брать `today` параметром, иначе тесты на фиксированной
  дате невозможны (сейчас так и сделано — надо сохранить).

### R5. PWA: `PRECACHE`, `CACHE`, устаревшая оболочка

* Каждый новый модуль (`js/models/obligation.js`, `js/limits.js`, `js/screens/budgets.js`,
  `js/components/obligationSheet.js`, `js/reports/*` при новых отчётах) обязан попасть
  в `PRECACHE` (`sw.js:10-53`) **и** поднять `CACHE` (`sw.js:6`). Контроль:
  `node scripts/check-precache.mjs` + pre-commit хук (`.githooks`).
* Опаснее другое: после деплоя v4 часть пользователей (телефон с установленной PWA) какое-то
  время получает **старый** закэшированный билд. Старый код увидит `schemaVersion: 4` и выдаст
  `UNSUPPORTED_VERSION` (`storage.js:52-53`) — «Данные созданы более новой версией приложения».
  Для единственного пользователя это выглядит как поломка после обновления. Митигация: не менять
  `schemaVersion` до того, как оболочка обновится (трудно) или сделать чтение v4 терпимым
  (данные + мягкий баннер «обновите приложение»), а не отказ. Это решение уровня архитектуры.
* `readState()` при любой ошибке возвращает `null`, а `loadState()` в этом случае **сеет seed
  и сохраняет его** (`storage.js:425-465`) — на обновлении схемы это опаснее, чем на обычном сбое.

### R6. Нет автотестов в репозитории

`AGENTS.md`: «автотестов в репозитории нет», `npm test` не запускается; внешний харнесс
`~/finance-tests` лежит вне репозитория и может отсутствовать. Следствия:

* Чистые функции обязательны: лимит, раскладка процентов, распределение нормы, урезание бюджетов
  должны жить в `js/` без DOM (как `payments.js`, `journal.js`), иначе их нельзя проверить ни
  внешним харнессом, ни будущими тестами (`AGENTS.md`: «`js/reports/*` не импортируют DOM»).
* NFR «пересчёт лимита и бюджетов ≤ 50 мс» и «первый экран < 1 с» проверить нечем — только
  вручную. Стоит либо снять эти NFR, либо добавить измеримую формулировку (например «лимит
  считается на каждом рендере без мемоизации, объём данных ≤ 5 000 операций»).
* Проверка перед сдачей — `docs/qa-checklist.md` вручную.

### R7. `validateState()` как единая точка отказа

Функция на 250 строк (`storage.js:167-414`) проверяет всё: типы, уникальность, ссылки. Новые
правила легко сделать слишком строгими и заблокировать уже сохранённые данные:

* `paymentDay: 1..31` — валидно, но `31` в феврале требует `clampDay`, а не «дата существует»;
* `annualRate > 0` сломает обязательство с беспроцентным займом (ставка 0) — а PRD говорит
  «все поля обязательны», не «больше нуля»;
* `savingsPercent` сумма ≤ 100 должна проверяться **на активных** счетах: архивный счёт с 60 %
  не должен блокировать создание нового (иначе архив нельзя обойти).

### R8. Чистота отчётов и инвариант `discrepancy`

`buildCashFlow` содержит самопроверку `discrepancy = (totalIn - totalOut) - (closing - opening)`
(`cashFlow.js:33-34`). Как только тело платежа по обязательству станет переводом на сущность,
которой нет в `state.accounts`, инвариант перестанет быть нулём. Если это не заметить, приёмка
FR-38 («остаток на конец совпадает с активами») пройдёт, а скрытая проверка — нет.
Обязательство **не должно** быть счётом в `accounts`: иначе оно попадёт в `totalBalance()`,
в «Всего на счетах» и в лимит (FR-27), что противоречит смыслу.

### R9. Идемпотентность и каскады

Автопереводы (FR-23/25) и оплата обязательства (FR-17) — единственные действия, которые
**создают** операции как побочный эффект. Требуется явная идемпотентность:

* повторное сохранение того же прихода не должно плодить переводы (сейчас `updateTransaction`
  полностью заменяет запись — `app.js:76-81`);
* удаление прихода (FR-25) — каскад по `sourceTransactionId`, но `deleteTransaction` сейчас
  удаляет только саму операцию (`app.js:61-68`);
* удаление счёта (FR-4): «счёт накоплений с созданными переводами не удаляется» — уже
  обеспечено `accountHasOperations()` (`accounts.js:6-10`), т.к. переводы — операции; дополнительная
  логика не нужна, но это стоит записать, чтобы не дублировать проверку.

## 5. Выводы по выполнимости (4 самых рискованных требования)

### 5.1 FR-16/17/18/19/20 — обязательства и раскладка платежа → **нужно дизайн-решение, потом схема**

Это не «добавить CRUD». Три независимых проблемы:

1. **Форма проводки.** Ни одна существующая форма операции не даёт «P&L 7 000, ДДС 25 000,
   долг −18 000» (C3). Нужен либо новый `type: 'loan'` с двумя суммами и правкой
   `transactionDelta`/`incomeStatement`/`cashFlow`/`overview`, либо пара «расход + перевод»
   с исключением тела из P&L на уровне отчёта. Второе ломает `discrepancy` и правило
   «переводы не входят в ДДС».
2. **Обратимость.** FR-8 + FR-20 противоречат друг другу (C8). Нужно правило отката тела
   при удалении/правке оплаты.
3. **Детерминизм процентов.** Хранить snapshot или пересчитывать (2.3) — влияет на закрытые
   отчёты и на объём localStorage.

Оценка: **дизайн-решение обязательно**, затем схема v4 + модель + 3 отчёта + календарь.
Сам CRUD (FR-15) — тривиален; риск целиком в деньгах и отчётах.

### 5.2 FR-27/28/29/30 — дневной лимит → **почти прямо, нужны 3 конвенции**

Чистая функция над `accounts` + `paymentOccurrences` + `plannedPayments`. Схема **не меняется**.
Развилки, которые PRD оставляет открытыми:

* делитель: 19 (пример PRD, сегодня не тратится) или 20 (сегодня входит);
* `skipped`-вхождения не резервируются (сейчас их отдаёт `collectOccurrences`, `payments.js:157-166`);
* архивные расходные счета: входят в базу или нет (FR-3 требует включать их в итоги, FR-27 молчит);
* «месяц от сегодня» — локальный календарный, с `clampDay` для конца месяца.

После фиксации конвенций — `js/limits.js` (+ тесты внешним харнессом), карточка на обзоре.
Это **самое дешёвое** из четырёх и даёт основную ценность (SM-1, UJ-1).

### 5.3 FR-2/22/23/24/25 — норма сбережений и автопереводы → **нужна миграция + решение по каскадам**

* Поле `account.savingsPercent` — механическая миграция (умолчание 0), но с ловушкой R1:
  `normalizeAccountInput()` (`accounts.js:21-41`) возвращает фиксированный объект и **потеряет**
  поле при редактировании счёта, если его не добавить. Плюс UI: `readAccountForm()`
  (`settings.js:192-210`) и `index.html:258-273` — новый контрол, `inputmode="decimal"` не нужен,
  это целое.
* Создание переводов — новая операция с `sourceTransactionId`; каскад на правку/удаление (C9)
  и идемпотентность (R9) — это дизайн-решение, не механика.
* Проверка суммы ≤ 100 % — на создании **и** редактировании, только по активным.

Оценка: **миграция + дизайн-решение по каскаду**. Средний риск, объём — 1–2 сессии.

### 5.4 FR-32/33/34/35 — бюджеты с урезанием → **дизайн-решение первым**

Модель `Budget` уже есть, UI нет; удаление категории каскадит (`app.js:269-281`). Но:

* FR-34 требует «исходный размер» и «восстановление». Хранить `effectiveAmount` в `state` —
  значит хранить производное и синхронизировать его при каждом изменении лимита; лучше
  вычислять при чтении, а `Budget.amount` оставить исходным. Это надо записать явно, иначе
  разработчик добавит поле и получит рассинхрон.
* «Пропорционально размеру бюджета; сумма урезанных равна свободным деньгам» (`prd.md:423`) —
  с целыми копейками сумма долей не сойдётся: нужен детерминированный раздатчик остатка
  (как при распределении процентов). PRD молчит.
* FR-33 «блокирует бюджет, если сумма превысит свободные деньги» + FR-34 «автоматически урезает»
  — два разных поведения на одно и то же состояние. Что происходит: отказ в сохранении или
  тихое урезание? Это открытый вопрос (PRD сам отмечает приоритеты как нерешённые, `prd.md:660`).
* FR-35: точка входа не выбрана (открытый вопрос 6) — а от неё зависит `router.js`/`tabFor`
  и `PRECACHE`.

Оценка: **сначала решить, что такое «свободные деньги» в момент сохранения** (снимок на момент
действия или живой пересчёт) и **что важнее — запрет или урезание**; после этого — обычный экран
плюс чистая функция. Без решения получится два противоречащих FR в одном экране.
